# smb2 0.30.0 in Cmdr: QA handoff (2026-10-14)

What changed for a person using Cmdr on an SMB share when Cmdr moved from `smb2` 0.29.0 to 0.30.0, how to see each
change, and what was proposed but not built. For the lead to turn into QA steps; delete once QA'd.

## Setup for the steps below

- **A NAS share**: connect to Testnas as usual (Cmdr's direct SMB connection, so the pane's SMB chip shows "direct").
- **A Docker share**: `apps/desktop/test/smb-servers/start.sh`, then in Cmdr connect to `smb://127.0.0.1:11480/public`
  (guest). `11492` is the `flaky` fixture (5 s up, 5 s down), `11493` the `slow` one (200 ms per round trip).
- **Forcing a reconnect**: on the NAS, turn the Mac's Wi-Fi off for about 10 s and back on (or restart the SMB service
  in QTS). On Docker, `docker restart smb-consumer-smb-consumer-guest-1`, or browse the `flaky` share. The pane shows
  the "unreachable" banner, then comes back by itself.
- Logs: `RUST_LOG=cmdr_smb=debug` (see `docs/tooling/logging.md`).

## 1. Replacing a file on a share is one atomic step

A forced rename is now smb2's `rename_with(replace_if_exists)`: the server swaps the new file in under the old name in
one step, so the old file never disappears on its own first. Commit `874011b87`.

- **Rename onto a taken name**: in a share pane, F2 a file (`a.txt`) to the name of another file in the same folder
  (`b.txt`), and choose to replace in the conflict dialog. Expect `b.txt` to hold `a.txt`'s contents and `a.txt` to be
  gone, as before. New: there's never a moment where neither file exists (hard to see by eye; the log shows one `rename`
  and no `delete_file` before it).
- **Compress over an existing ZIP on a share**: select files in a share pane, compress to a name that already exists in
  that folder, and replace it. Expect the new ZIP under the old name. New: no `<name> (recovered)` aside file is ever
  created, even briefly, and the replace is faster (it used to set the original aside, rename, then delete it).
- **Edge: a folder in the way.** Rename a file or folder onto an existing EMPTY folder with replace: still works (the
  folder is cleared first, as before). Onto a NON-empty folder: still refused, nothing changes.
- **Edge: Read-only or open destination.** On the NAS, replacing a file another app has open, or one marked Locked:
  Samba replaces it anyway (expected, smb2 documents it); a Windows server would refuse, and the original stays put.

## 2. A case-only rename no longer loses or refuses the file

Three bugs, same cause (Cmdr asked "does the new name exist?" and a case-insensitive share said yes, because it's the
same file). Commits `874011b87`, `aba9a20df`, and the F2 conflict-check fix after them.

- **Plain case-only rename**: in a share pane, F2 `report.txt` to `Report.txt`. Before: first the conflict dialog ("A
  file with this name already exists", comparing the file with itself), then, past it, refused as "already exists". Now:
  no dialog, it renames, the listing shows `Report.txt`, contents intact. Same for a folder (`album` → `Album`). The
  dialog came from F2's pre-check (`check_rename_validity_impl`), which only knew the local disk's inode test for "the
  target is the source"; off the local disk it now asks the folder's listing.
- **Forced case-only rename** (data loss before): a rename WITH replace whose target differs only in case used to DELETE
  the file and then fail. The pane's F2 path now sends a case-only rename without replace (it asks nothing), so this is
  hard to reach by hand (an undo or rollback of a rename passes replace through); the Docker test pins it. Expect the
  file to survive.
- Multi-rename (⌃M) on a share with a case-change rule exercises the plain case-only path across many files.

## 3. A big folder on a share shows progress, and leaving it stops the listing

Every SMB listing now arrives one server batch (a few hundred entries) at a time. Commit `be16dc023`.

- **Progress**: open a folder with thousands of files on the NAS (Google Takeout photos is ideal), or on Docker create
  one (`smb-consumer-manyfiles` from `start.sh all` has 10,000+ files, port 11487). Expect the pane's "Loaded N entries"
  line to climb while it loads. Before: nothing, then the whole folder at once. Easiest to see on the `slow` fixture or
  the NAS over Tailscale.
- **Cancel**: open that big folder and press Esc (or navigate elsewhere) while it's still loading. Expect the pane to
  move on at once, and the next listing of anything on the share not to wait behind the abandoned one. Before: the share
  kept reading the whole folder in the background.
- **Index scan**: a share index scan that's stopped while it's inside a huge folder now stops at the next batch rather
  than finishing that folder first.
- **Not changed**: the pane still renders the folder once it's complete (rows don't stream in progressively; that's
  proposal A below). Sorting, counts, and what's listed are identical.

## 4. A reconnect can't pair an old share handle with the new session

Internal, no UI. Cmdr kept the client and the share's tree behind two locks; a reconnect landing between reading the two
handed an operation the old tree with the new connection. smb2 0.30 refuses that pair, which Cmdr would have read as the
session dying again. Commits `7389c370a` and `f2ef6c30b`.

- **What to try**: start a large copy to the NAS, force a reconnect mid-copy (see Setup), and browse the share while it
  recovers. Expect one "unreachable" blip, then the copy continuing or retrying its current file, and browsing working
  as before. Not expected: a second disconnect right after the share came back, or a copy failing with "the server
  disconnected" right after the reconnect.
- **Not changed**: what a reconnect looks like, how long it takes, the "Sign in" prompt on a changed password.

## 5. The share password stays out of logs

`SmbConnectionParams` printed the password in `{:?}` output; it now prints `***`. smb2 0.30 does the same for its own
types. Commit `36ba541b9`. Nothing to click; with `RUST_LOG=cmdr_smb=trace`, connect to an authenticated share and grep
the log for the password: no hits.

## What not to expect to change

- Copy and move speed, progress, and the transfer tree: no transfer-path behavior changed.
- The watcher (live updates from other clients), Finder drags out of a share, the share list, and the server sign-in
  flow.
- Uploads interrupted by a disconnect still restart the file from the beginning (proposal B).

## Proposals not built

**A. Show a big share folder's rows as they arrive.**

- Problem: the pane renders a listing only once it's complete, so a 100,000-entry share folder shows a counter for
  seconds before any row.
- Impact: big NAS folders (photo libraries, Takeout dumps) feel slow; the data is already arriving batch by batch.
- Solution: let `Volume` hand the listing engine batches (a streaming `list_directory` variant), and have `cmdr-listing`
  render a provisional, unsorted-then-resorted view. SMB already reads in batches (item 3).
- Size: L (listing engine, sorting, cache, selection stability, frontend). Tradeoff: rows reshuffle as later batches
  sort in, which is a design call.

**B. Resume an interrupted upload to a share instead of restarting it.**

- Problem: a disconnect mid-upload makes the per-file retry start that file from byte zero; a 20 GB video over a flaky
  link can loop.
- Impact: large uploads to the NAS over Wi-Fi or Tailscale.
- Solution: checkpoint with `FileWriter::flush_checkpoint` every N MB, and on retry call `resume_file_writer` with the
  checkpoint, re-reading the source from its offset (`open_read_stream_at_offset` exists). Fall back to a fresh upload
  on `ResumeRefused`. Optionally persist the `WriteCheckpoint` (serde) for resume across an app restart.
- Size: M within one run (the transfer retry layer plus `write_from_stream`), L across restarts (journal, UI). Tradeoff:
  each checkpoint is a server FLUSH (some throughput), and the staging temp naming has to stay coherent.

**C. Land a replaced file in a copy with one atomic rename where the volume supports it.**

- Problem: the copy's conflict "Replace" and the staged-write landing clear the destination (set aside or delete) and
  then rename, on every backend.
- Impact: three round trips instead of one per replaced file on SMB, and a window where the name is empty.
- Solution: in `staged_write::land` and `finalize::finalize_safe_replace`, use `rename(force = true)` when
  `supports_atomic_replace_rename()` (now true for SMB and local).
- Size: S–M, but it changes the transfer layer for local disk too, which its docs deliberately shaped. Tradeoff: needs
  the transfer owner's eyes on the crash-safety story.

**D. Notice metadata-only changes and renames on a share.**

- Problem: the share index and listings compare size and modified date, so a Hidden flag or date change made elsewhere
  isn't seen until a full rescan, and a rename reads as a delete plus a new file.
- Impact: index freshness and media enrichment redo work after renames on the NAS.
- Solution: carry smb2's `changed` time into the index's freshness check, and opt into listing `index_number`
  (`ListOptions::index_numbers`) as `FileEntry::inode` for rename detection. `stat_with_identity` answers "is this the
  same file?" for one path.
- Size: M. Tradeoff: `inode` also drives hardlink dedupe in size totals, so mapping it on SMB changes those numbers;
  needs a decision.
