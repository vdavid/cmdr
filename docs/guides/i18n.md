# Internationalization (i18n)

The desktop frontend is fully i18n-ized: every user-facing string lives in a message catalog and resolves at runtime. 13
catalogs ship: source `en`, 10 full translations (`de`, `es`, `fr`, `hu`, `nl`, `pt`, `sv`, `vi`, `zh`, `zh-Hant`), and
two regional overlays of `en` (`en-GB`, `en-AU`). Adding another needs no code changes. This guide is the map + the
cross-cutting workflows; per-area mechanics live in the colocated docs it points to (single source, so don't restate
them).

## Architecture (where things live)

- **Runtime**: `apps/desktop/src/lib/intl/` (read its `apps/desktop/src/lib/intl/CLAUDE.md` + `DETAILS.md`). Two locale
  sources, one per consumer:
  - the **message runtime** (`messages.svelte.ts`): `t(key, params?)` (catalog + ICU via `intl-messageformat`),
    `getMessage(key)` (raw lookup, no ICU), `setLocale()`, the locale-version rune, the compiled-message cache;
    `Trans.svelte` for sentences with an inline interactive component; `keys.gen.ts` (the generated `MessageKey` union,
    never hand-edit).
  - the **locale-aware formatter layer** (`locale.ts`, `number-format.ts`, plus dates in
    `$lib/settings/format-utils.ts`): numbers, file sizes, and dates, all on `getFormatLocale()`, which follows the OS
    rather than the `appearance.language` setting.
- **Native surfaces**: `apps/desktop/src-tauri/src/intl/native_strings.rs`. The menu bar, the main window's title, and
  the already-running alert are drawn by the OS, not the webview, so Rust resolves them itself with `menu_t(key)` from a
  generated table (`pnpm intl:native-strings`). Same catalogs, same checks, no ICU. Read
  `apps/desktop/src-tauri/src/intl/DETAILS.md` § The strings Rust draws itself before touching a `menu.*` key.
- **Catalog**: `apps/desktop/src/lib/intl/messages/en/<area>.json`, one file per feature area (read its
  `apps/desktop/src/lib/intl/messages/CLAUDE.md` + `DETAILS.md`). 3,263 keys across 35 files per locale (counted
  2026-09-05: non-`@` keys in `apps/desktop/src/lib/intl/messages/en/*.json`). Key prefix ↔ filename is 1:1
  (`settings.fsWatch.title` → `settings.json`). `common.json` holds genuinely shared strings. ARB-style `@key` sibling
  entries carry the translator `description` (+ `placeholders` map, + optional `screenshot`), stripped before the
  runtime/codegen ever see them.
- **Enforcement** (checks, all green on every build):
  - `cmdr/no-raw-user-facing-string` (ESLint, `apps/desktop/eslint-plugins/`): flags a hardcoded string in a known sink
    (`title`/`label`/`placeholder`/`aria-label` props, `addToast(...)` args, `.svelte` text) in any migrated area. The
    enforced-area list is the whole frontend now; its exclusion ledger is empty.
  - `desktop-message-key-naming` + `desktop-message-keys-fresh` (Go, `scripts/check/checks/`): key shape
    `area.feature.leaf` against a closed area set, and `keys.gen.ts` freshness.
  - `desktop-shipped-locales-fresh` (Go, nickname `shipped-locales-fresh`): the Rust locale resolver's table of shipped
    catalogs and their CLDR scripts (`src-tauri/src/intl/shipped_locales.gen.rs`, from `pnpm intl:shipped-locales`).
    Adding a locale dir without regenerating would leave it unreachable by auto-selection and unguarded against a script
    mismatch. Details: `apps/desktop/src-tauri/src/intl/DETAILS.md`.
  - `desktop-native-strings-fresh` (Go, nickname `native-strings-fresh`): the Rust-side table of the strings Rust draws
    itself (`src-tauri/src/intl/native_strings.gen.rs`, from `pnpm intl:native-strings`). A stale table is invisible in
    the worst way: the menu bar keeps drawing the OLD label, so a copy fix or a landed translation silently doesn't
    ship.
  - `desktop-message-keys-unused` (Go): error-level orphan check. A catalog key referenced in neither
    `apps/desktop/src/` nor `apps/desktop/src-tauri/src/` is dead translation work (real money once human translators
    are involved), so it fails the build. It scans Rust because the `menu.*` keys are used from there and would
    otherwise read as ~130 orphans. Runtime-built keys are carried by a closed, documented dynamic-prefix allowlist;
    canonical detail lives in `apps/desktop/src/lib/intl/messages/DETAILS.md` § Dead-key honesty + the orphan check.
  - `desktop-i18n-stale` (Go, nickname `i18n-stale`): WARN-only in normal runs. Flags a non-`en` translation whose
    stored `@key.sourceHash` no longer matches the hash of the value it was translated from (English, or for an overlay
    the value it overrides), plus a missing hash, a removed source, and a stale key still marked `reviewed: true`. The
    release flow sets `CMDR_I18N_STALE_STRICT=1`, which escalates a finding to a build-failing error, so a release can't
    ship stale copy. Detail: `messages/DETAILS.md` § `@key` schema (`sourceHash` / `reviewed`).
  - **The locale-validation checks** (Go wrappers over Node `runLocaleCheck` scripts, running against all 12 non-`en`
    locales). Four are ERROR class (they fail the build and get real CI steps):
    - `desktop-i18n-parity` (`i18n-parity`): each non-`en` key's `{placeholder}`+`<tag>` set (ICU keys) or `{token}` set
      (raw `errors.*`) must EQUAL that of the value it renders instead of (English, or for an overlay the value it
      overrides). A missing/renamed/extra arg is the #1 runtime crash class.
    - `desktop-i18n-icu` (`i18n-icu`): every message is written in the grammar of its own family, which is two mirrored
      rules. An ICU message must compile via `intl-messageformat`. A RAW value (`errors.*` plus the native `menu.*`
      families, see § Error pipeline below) is not parsed as ICU at all, and must not carry ICU escaping: nothing
      collapses a doubled `''` on that path, so it reaches the real macOS menu bar as two apostrophes. `en` is checked
      alongside the locales here, unlike the other locale checks: this rule is about a catalog's own syntax, not about a
      translation's standing against its source.
    - `desktop-i18n-plural` (`i18n-plural`): each `plural` arg covers the LOCALE's required CLDR categories (data-driven
      from `Intl.PluralRules`), gated on the English source's own plural shape (a deliberately `other`-only English
      plural doesn't force few/many on a richer locale).
    - `desktop-i18n-coverage` (`i18n-coverage`): honest coverage so a "100% translated" claim is trustworthy, read per
      locale KIND. A full translation must cover every English key: MISSING (silent English fallback) or still-English
      (likely untranslated) is a finding. Still-English means byte-IDENTICAL, or SOURCE-TEXT-ONLY: a value whose only
      difference from English is which plural/select categories it branches on, so the branch set is the locale's own
      and every branch's TEXT is English. That second shape is why English counters once shipped inside a locale this
      check called fully covered (Portuguese requires a `many` category English lacks, so a copied-through counter is
      never byte-identical). A legitimately English value (a brand, a unit symbol, a placeholder-only string, a loanword
      the locale shares) is exempted from BOTH signals by a non-empty `@key.sameAsSourceJustification` in the locale
      catalog (the translator's reason), while MISSING is never suppressed. An OVERLAY inverts it: missing is expected,
      identical-to-what-it-overrides and unknown keys are the findings, and no justification applies. Field + workflow:
      `i18n-translation.md` § Deliberately-identical strings; overlay rules: § Overlay catalogs below. Unlike the other
      three, a failure here isn't a runtime break: it gates the build because a half-translated locale is exactly the
      kind of headline a warn-only signal lets slip into a release.

    Two are WARN class (quality/maintenance, never block the build, `NotInCI` like the stale check):
    - `desktop-i18n-dont-translate` (`i18n-dont-translate`): warns when a curated brand/system token English carries for
      a key was dropped in the locale. The curated list (`BRAND_WORDS` + `SYSTEM_TOKENS`) lives in
      `i18n-catalog-lib.ts`.
    - `desktop-i18n-term-consistency` (`i18n-terms`): the only CROSS-KEY check. Warns when one locale gives a single
      English string two different names, so the menu item and the dialog it opens disagree. Its allowlist demands a
      REASON per accepted split; see § Term consistency below.
    - `desktop-i18n-aria-label` (`i18n-aria`): FAILS when a translated accessible name stopped CONTAINING its visible
      label (WCAG 2.5.3), which leaves voice-control users unable to press the control. Error class, because a
      regression here is silent for exactly the users it locks out. No allowlist and nothing grandfathered: a pair only
      counts when English's own `fooAria` contains `foo`, so the `*Aria` keys that aren't accessible names are never
      reported, and every shipped locale passes.

- **Maintenance tooling**: two shared, language-agnostic helpers the pseudolocale generator and the locale checks build
  on:
  - `apps/desktop/scripts/i18n-catalog-lib.ts`: load a locale's merged catalog (messages vs `@key` metadata split),
    enumerate locales/keys, classify each one (`resolveLocaleSource`: full translation or overlay, and which catalog it
    overrides), parse a message to its ICU structure (`parseMessage` → placeholders, `<tag>`s, plural/select categories,
    `ok`/`error`) via the runtime's own `intl-messageformat` engine, and `sourceHash(value)` (the 7-char hex source
    hash). The single source for "what tokens/structure does this message have", and for what a locale overrides.
  - `apps/desktop/scripts/i18n-locale-check-lib.ts`: the reusable per-locale check scaffolding every locale check
    (stale, parity, ICU, plural, coverage, don't-translate) follows: `localesToCheck()` (non-`en` locales), the
    `newFindings` accumulator, `reportFindings` (honest per-locale report), and `runLocaleCheck` (the
    resolve-each-locale's-source → inspect → report loop), plus the `EXIT_CLEAN`/`EXIT_ISSUES`/`EXIT_ERROR` exit-code
    contract that the `desktop-i18n-*` Go wrappers map (exit 1 → WARN, other non-zero → ERROR). A new locale check is a
    thin script over `runLocaleCheck` + a Go wrapper modeled on `desktop-i18n-stale.go`. The file header documents the
    pattern in full.

## Why this shape (rejected alternatives)

The whole system is owned, not adopted. The reasoning, so a future "why didn't we just use a library?" has an answer:

- **Custom thin runtime, not a framework** (Paraglide / i18next / svelte-i18n / Lingui). The hard part of i18n is the
  message FORMAT (per-locale plurals, multi-variable selection), not the lookup. We take the hard part from a focused
  library (`intl-messageformat`) and own the ~180-line runtime around it. i18next is a framework whose value-add
  (namespaces, backends, language detection, a React `<Trans>`) is mostly stuff we don't need (we bundle JSON, scope by
  key prefix) or can't use (React-only `<Trans>`). Paraglide has no English-as-key, no `@key` description/screenshot
  metadata, and no reactive rune. svelte-i18n is dormant; Lingui has no maintained Svelte integration. Owning a thin
  runtime fits Cmdr's principles (smart backend / thin frontend, here for the long run, agents read all the code).
- **ICU MessageFormat 1 (`intl-messageformat`), not MessageFormat 2** (`@messageformat/core`). MF1 is the broadly
  understood standard every TMS and most LLMs know, which matters for the agent-translation pipeline; it's mature and
  stable, and its rich-text tag handlers are the mechanism `<Trans>` builds on. MF2 is the newer standard with less
  tooling/LLM familiarity today: a future option, not adopted now.
- **JSON catalogs in git, no TMS.** A TMS earns its keep only with non-developer human translators, translation memory,
  and a review UI. Cmdr has none of those: agents translate, the pipeline is scripted, everything is version-controlled
  and diffable. JSON is native to JS and agent-friendly.
- **Semantic scoped keys (`area.feature.leaf`), not English-as-key.** English-as-key orphans every translation the
  moment copy is edited; semantic keys survive copy edits. Scoping is free because the key path IS the scope: the same
  English word diverges per window just by getting its own key (shared strings live in `common.*`).

## Add or change a user-facing string (the everyday task)

1. Add the message to the right `messages/en/<area>.json` with a semantic key `area.feature.leaf` (lowerCamel) and a
   sibling `@key` with a translator `description` (+ `placeholders` if it interpolates). Pick the area = the feature
   dir.
2. Resolve it at the call site: `t('area.feature.leaf', { … })` for static/plural/select copy; `<Trans>` when a
   component sits mid-sentence; `getMessage(...)` only for the error pipeline (see Gotchas). Never hardcode the literal.
3. Run `pnpm intl:keys` to regenerate `keys.gen.ts` (the typed `MessageKey` union; a missing key is a compile error, an
   unused catalog key is a dead-key warning).
4. Keep the area's `*-i18n-parity.test.ts` green (it pins base-en output byte-for-byte). A copy edit changes the catalog
   value AND the parity test together.

A `menu.*` string is the exception to steps 2 and 3: it's resolved in Rust with `menu_t('menu.…')`, and the extra step
is `pnpm intl:native-strings` (from `apps/desktop/`) to refresh the table the crate compiles in. Its `@key` description
carries more weight than usual, because no screenshot can ever show a native menu; say which menu the item sits in, what
activating it does, and whether the English word is a VERB or a NOUN.

Conventions: ICU message **values** double every apostrophe (`''`); `@key` metadata (descriptions/placeholders) uses
**normal** apostrophes (it's not ICU). Embed counts as preformatted `*Text` string params (formatting is single-sourced
in `$lib/intl`), passing the raw integer alongside only to drive `plural` selection. Full `@key` description guidance +
the litmus test: `messages/DETAILS.md` § `@key` metadata schema.

## Add a new locale (future localization)

The step-by-step translator process (pick tag → skeleton → style guide → translate → checks → review → ship) is in
`i18n-translation.md` § Add a new language. This section is the runtime/mechanism side.

No code changes: that's the whole point of the readiness work. Create `messages/<locale>/<area>.json` files mirroring
`en/` (same keys, translated values). The runtime's glob (`messages/*/*.json`) already loads every locale dir keyed by
its tag, so a new dir is picked up at build with no edit, and it auto-appears in the Settings > Appearance > Language
picker (`availableLocales()`). `setLocale(locale)` switches at runtime (reactive: markup re-renders; plain-`.ts` reads
are snapshots). Dates/numbers/sizes already follow the active locale via the formatter layer.

### Locale-format convention (BCP-47, language-base fallback)

The locale VALUE is a full BCP-47 tag (`en-US`, `de-DE`, `pt-BR`): `getUiLocale()` for catalog resolution,
`getFormatLocale()` for numbers, sizes, and dates. Don't change that.

Catalogs are keyed by BCP-47, with the **language base** as the universal fallback:

- `en` is the base (the source locale) and the FINAL fallback.
- A **language-base** catalog (`de`, `pt`) holds a full set for that language.
- A **region-variant** catalog (`en-GB`, `pt-BR`) is an OVERLAY: it holds only the keys that differ from its base (see
  below).

**Resolution** for an active locale `xx-YY`: try catalog `xx-YY` → try `xx` → fall back to `en` → the key itself (so a
missing key is visible, never a crash). The active locale is `getUiLocale()`. British English, for example, is
`add an en-GB catalog` and the resolver prefers it over `en`.

The resolver and the language selector are BUILT. `messages.svelte.ts` loads every `messages/<locale>/` dir (the glob
keys catalogs by the dir's BCP-47 tag and filters out non-locale dirs like `screenshots/`), and `resolveRaw` does the
fallback above per key. The in-app picker is **Settings > Appearance > Language** (`appearance.language` setting):
"System default" (follow the OS) plus one option per loaded locale, each labeled with the locale's own endonym via
`Intl.DisplayNames`. `settings-applier.ts` maps the choice to `setLocale`, so switching applies immediately (no Apply
button, no restart), and the choice persists across restarts (applied at startup from the stored value). Locale is
frontend-only, so there's no Tauri command. Note BCP-47 tag NAMES (`en`, `en-GB`, `pt-BR`) are format identifiers, not
translatable content.

## Overlay catalogs (regional variants)

A locale is an **overlay** when its language base ALSO ships a catalog. `en-GB` and `en-AU` are ones (`en` always
ships), `pt-PT` becomes one the moment `pt` ships. An overlay carries ONLY the keys it deliberately forks: `en-GB`
carries 151 of the 3,263 keys and `en-AU` 161 ("Trash" → "Bin", "colour", "favourite", "licence"), and every other key
resolves through the fallback chain above. Cloning the full catalog to change 151 strings would mean re-reviewing
roughly 3,100 identical strings forever.

**An overlay does NOT inherit from a sibling overlay.** `en-AU` resolves to `en`, never to `en-GB`, so every British
form the two share is written into both catalogs (149 of `en-AU`'s 159 keys are byte-identical to `en-GB`'s). That
duplication is the inheritance rule working as designed: a chain that skipped it would tell the checks a catalog may
fall back somewhere the runtime never looks.

The three kinds, and what each is checked against:

- **The base**, `en`: the source everything else falls back to.
- **A full translation** (`de`, `hu`, and the generated `en-XA`): must cover every English key. A bare language tag is
  always one, and so is any variant with nothing to inherit: `fr-CA` with no `fr` catalog, and `zh-Hant` against a
  Simplified `zh` (see the script rule below).
- **An overlay** (`en-GB`, `en-AU`, `pt-PT`): carries only its forks, checked against **the catalog it overrides**,
  which is its language base layered over `en` (for `pt-PT`: exactly what a `pt` reader sees today). For `en-GB` those
  are the same catalog; for `pt-PT` they are not, and every check uses the `pt` value, never the English one.

**A script boundary is never an overlay.** Inheriting only helps when the reader can READ what they inherit, so a
variant is an overlay only when it's the same LANGUAGE and the same SCRIPT as the catalog below it. `en-GB` over `en`
and `pt-PT` over `pt` qualify; `zh-Hant` over Simplified `zh` does not, and neither does `zh-TW` (CLDR says that region
is Traditional even though the tag names no script). A Traditional catalog is therefore a FULL translation: its missing
keys fall back to English, never to Simplified. Calling it an overlay would tell its translator "skip what matches your
base" about text their readers can't read. Canonical rationale: `apps/desktop/src-tauri/src/intl/DETAILS.md` § The
script guard, and why regional fallback survives it.

The classification lives in ONE place, `resolveLocaleSource` in `apps/desktop/scripts/i18n-catalog-lib.ts`, which
resolves it per locale and hands every check the answer plus the catalog to compare against. It asks
`inheritableAncestors` (`apps/desktop/src/lib/intl/locale-inheritance.ts`) for the nearest ancestor tag that exists and
reads the same script, which is the SAME function the message runtime resolves keys through, so a checker can never be
more permissive than the app. With a `zh-Hant` catalog shipped, `zh-Hant-TW` overlays `zh-Hant`; without one, it's a
full translation.

### What each check does with an overlay

- **`desktop-i18n-coverage`** (ERROR) inverts. A missing key is correct (that's the point of an overlay), never a
  finding. A value byte-identical to the catalog it overrides IS a finding: it forks nothing, and it freezes a copy of a
  string that will drift. A key in neither the overridden catalog nor `en` is a finding too: an overlay must not invent
  keys, since nothing would ever render one.
- **`desktop-i18n-parity`** (ERROR) compares `{placeholder}` / `<tag>` / raw `{token}` sets against the overridden
  value, so a `pt-PT` fork must match `pt`'s structure.
- **`desktop-i18n-stale`** (WARN; ERROR at release) hashes the overridden value into `@key.sourceHash`. A `pt` copy edit
  marks the `pt-PT` fork of that key stale and clears its `reviewed` flag; an unrelated `en` edit that `pt` already
  absorbed does not.
- **`desktop-i18n-icu`**, **`desktop-i18n-plural`**, and **`desktop-i18n-dont-translate`** work per key on whatever the
  locale defines, so they need no special case: an overlay's few keys are checked, the absent ones aren't.

**No check compares an overlay to its SIBLING, or to its own vocabulary.** Every one above measures a catalog against
the one it overrides, key set by key set, so two failures slip through them all: `en-AU` drifting from `en-GB` on a form
both are supposed to share, and a term that forks in one area file while the American spelling survives in another. The
vitest suite `apps/desktop/scripts/i18n-en-overlays.test.ts` is that missing comparison. It pins the AU-only divergence
list, sweeps every base-`en` value for each forked term in `docs/i18n/en-GB/glossary.md` (matching only the literal
text, via `visibleLiterals`, so a `{colorName}` placeholder or a ` trash {` selector never counts as copy), and
re-checks placeholder/tag parity plus `*Aria`-contains-its-label. Extend the term table there when the glossary grows.

The Go wrappers deliberately don't classify: they count locales for their success lines and leave the overlay question
to the TypeScript, because answering it needs the CLDR script data Node's `Intl` has and Go doesn't.

`@key.sameAsSourceJustification` is deliberately **NOT honoured on an overlay**. On a full translation an
identical-to-English value can be genuinely correct (a brand, a unit), so it needs a recorded reason. On an overlay the
fix is always "delete the key": the fallback renders that exact string anyway, so a justification could only argue for
keeping something that changes nothing while quietly pinning a stale copy. Fields that DO apply: `sourceHash` (of the
overridden value) and `reviewed`.

### Adding an overlay

1. Create `messages/<tag>/` with only the area files you fork, holding only the keys that genuinely differ. Everything
   else is inherited, so don't copy it. (First confirm it IS an overlay: a different-script variant inherits nothing and
   is a full translation instead.)
2. Stamp each key's `@key.sourceHash` with the hash of the value it OVERRIDES (the base language's value, or `en`'s when
   the base doesn't define that key), not the English one, unless they're the same catalog. `gen-locale-skeleton.ts`
   mirrors the whole `en` catalog, so it refuses an overlay tag; `sync-locale-keys.ts` skips overlays for the same
   reason.
3. Run the checks (`i18n-translation.md` § Add a new language, step 5). Coverage tells you which keys are dead weight.

## Term consistency (the only cross-key check)

Every other i18n check reads ONE key against its source. That structure is why a whole defect class kept shipping: a
locale rendering one English string two ways is invisible per key, and only shows up when a user walks from one surface
to the next. Traditional Chinese shipped a menu item reading `命令選擇區…` that opened a palette titled `指令面板`, and
a menu item `輸入授權金鑰…` that opened a dialog titled `輸入授權碼`. Both passed every check.

`desktop-i18n-term-consistency` groups keys by their normalized SOURCE value and compares what the locale renders for
each. For an overlay it compares the EFFECTIVE value (the overlay's where it forks a key, the base catalog's where it
doesn't), so a half-forked term is caught even though each key alone looks right.

Normalization ignores punctuation that WRAPS a term at either end (a trailing colon or ellipsis, French's spaced `!`,
Spanish's opening `¿`, a full-width `。`), so `Copié !` and `Copié` are one rendering. It keeps case, so a sentence-case
label and a Title Case menu item stay distinct, and it keeps `%` and `{placeholder}` braces, which belong to the term.

**The allowlist demands a reason, and that's the whole design.** Many same-English pairs SHOULD diverge, because English
is doing two jobs with one word: `Done` is a screen-reader word after a checklist step in one place and an operation's
lifecycle status in another; `View` is the F3 verb in one place and the View MENU in another. No checker can tell those
from real drift, so it doesn't try. It refuses to go quiet until the boundary is written down next to the term, in
`apps/desktop/scripts/i18n-term-consistency-allowlist.json`. An entry with a blank `reason` silences nothing.

Locales that predate the check carry a `notYetReviewed` COUNT rather than per-term entries, so nine untriaged locales
report one line each instead of ~300 findings that would train everyone to ignore the check. That count only ratchets
DOWN (on local runs), and a locale in neither section is strict from its first day.

**What it cannot see**: a term rendered inconsistently across keys whose ENGLISH differs ("Show thumbnails" vs
"Thumbnail size"). Deciding which English words are "terms" is the judgment no check has, so that half stays manual. The
recipe is in `docs/guides/i18n-translation.md` § Auditing a finished locale for term drift.

## Translating (the translator process)

The full translator-facing workflow (add-a-language step by step, the new-feature maintenance loop, and a reusable
agent-handoff system prompt) lives in the sibling guide `i18n-translation.md`. In brief: translation is agent-driven and
human-reviewed (principle 6), set up with three inputs kept separate:

- **Per-string context** = the `@key` `description` + `placeholders` (surface, trigger, constraints, do-not-translate
  tokens, plain-language placeholder meanings). Already authored for every key.
- **Per-language style guide** (you write, once per language) = tone, voice, formality, terminology/glossary. NOT
  per-string, so never repeat tone on every key.
- **One ICU instruction** in the agent's system prompt: preserve the placeholder / `plural` / `select` syntax, translate
  only the human text, and use the TARGET language's CLDR plural categories (which can differ from English's two). ICU
  is a formatter, not a translator: it selects + fills; all grammar correctness comes from the authored per-locale
  strings.

Two blind-translation risks the prompt and the description bar both call out: pass-through placeholders
(`{message}`/`{reason}`/raw `{path}`) carry uncontrolled runtime text, and fragment keys assemble via a named `*Join`
key (mind word order). Screenshots (below) add visual context. The error pipeline inverts the ICU rules (below).

## Pseudolocale (`en-XA`)

The pseudolocale is a generated locale that takes each English value and produces a deterministic, accented,
~+40%-longer string while preserving every `{placeholder}`, `<tag>`, and ICU `plural`/`select`/`#` structure, plus a
`@key.sourceHash` per key. It exists for two jobs:

- **Overflow testing.** The accented, deliberately-longer text makes clipping and layout breakage obvious when the app
  is driven in `en-XA` and screenshotted. After `pnpm i18n:pseudo`, `en-XA` loads like any locale and appears in
  Settings > Appearance > Language, so you can switch to it and watch the UI expand/accent live (a quick check that the
  resolver works). For the full sweep, run **`pnpm i18n:overflow`** (see below): it's the empirical "find the tight
  spots" tool, replacing guesswork about per-string max lengths.
- **Check fixture.** It's a complete, structurally-faithful non-`en` locale, so the stale check and the
  parity/ICU/plural/key checks can run against a real locale before any human translation exists.

Regenerate with **`pnpm i18n:pseudo`** (root) or in the desktop app. It's deterministic: same English in →
byte-identical pseudo out, so re-running is a no-op diff.

To validate the freshly-generated `en-XA` against the locale checks, run the `i18n-check-*.js` scripts **directly**
(e.g. `node apps/desktop/scripts/i18n-check-parity.ts`) or `pnpm check --fresh i18n-parity …`. Plain `pnpm check` can
serve a stale cached pass, because `en-XA` is gitignored and so isn't part of the checks' input fingerprint. A real,
committed locale IS fingerprinted, so this caveat applies only to the throwaway pseudolocale.

The generator (`apps/desktop/scripts/gen-pseudolocale.ts`) takes two transform paths, matching the runtime's `t()` vs
`getMessage()` split (see `apps/desktop/src/lib/error-messages/CLAUDE.md`): walk the ICU AST and transform only literal
text nodes for normal keys, and a letter-run tokenizer that leaves every `{token}`, literal `<…>`, and markdown char
untouched for the raw `errors.*` family. Both paths also keep the curated brand/system words (`BRAND_WORDS` in
`i18n-catalog-lib.ts`: Cmdr, macOS, GitHub, …) verbatim, so en-XA is a faithful translation simulation that passes the
don't-translate check too. Both reuse the shared helper (`i18n-catalog-lib.ts`); the test asserts `parseMessage(pseudo)`
token sets equal the English source's for every key.

What's tracked vs not:

- The **full `messages/en-XA/`** dir is **gitignored + regenerable** (like the screenshot PNGs); it's derived from `en/`
  and churns on every copy edit.
- A **small, committed, hand-verifiable fixture** lives in `apps/desktop/test/fixtures/i18n-pseudolocale/` (an `en/` +
  `en-XA/` pair covering a plain label, a placeholder, a tag, a plural, a select, a multi-placeholder sentence, a raw
  error, and a brand-word line). The stale + locale-validation check tests run against THIS fixture, not the gitignored
  full dir. Regenerate it with `node apps/desktop/test/fixtures/i18n-pseudolocale/gen-fixture.js` after changing the
  generator's transform.

### Overflow capture (`pnpm i18n:overflow`)

**`pnpm i18n:overflow`** drives every UI surface in the pseudolocale and screenshots it, so a human or agent can spot
text that clips, truncates, or breaks layout BEFORE any real translation lands. It's the empirical way to find tight
spots, instead of guessing a per-string max length.

It reuses the screenshot-capture harness (the same surface list as `pnpm i18n:shots`) via a `--locale` axis on the
driver (`pnpm i18n:capture --build --locale en-XA`): it regenerates `en-XA`, builds the capture binary (so the catalog
glob bakes `en-XA` in: the dir must exist BEFORE the build, which `i18n:overflow` handles), launches, switches the app
to `en-XA` through the capture API's `setLocale` (frontend-only, identical to the live Language picker), and captures
the main-pass surfaces. The mock-license/FDA passes are coupling-only and skipped here.

It produces, all in `messages/screenshots/overflow/` (gitignored + regenerable, kept fully SEPARATE from the coupling
screenshots, and it never touches `@key.screenshot`):

- one screenshot per surface, rendered in the expanded, accented strings, and
- **`overflow-report.md`**, a clip report. While each surface is rendered, a best-effort DOM scan flags text-bearing
  elements whose own box clips the content (`scrollWidth > clientWidth` or `scrollHeight > clientHeight` while
  `overflow` is hidden/clipped/ellipsed), listing per surface the elements that overflow. This turns "eyeball 66
  screenshots" into "here are the N spots that actually overflow". It skips visually-hidden `sr-only` nodes (they clip
  by design). It's a HEURISTIC, documented as such: it can miss a clip an ancestor masks, and can flag a
  deliberately-ellipsized label that's fine, so treat it as a list of spots to eyeball against the matching screenshot,
  not a pass/fail gate.

## Screenshots

Each `@key` can carry a `screenshot` filename (in `messages/screenshots/`) showing the string in the running UI; one
screenshot serves many keys. The harness is shipped and re-runnable: `pnpm i18n:shots` captures fresh screenshots and
rewrites the `@key.screenshot` couplings in one command. Reach for it after a UI change.

How it works (mechanism lives with the code, see `apps/desktop/src/lib/intl/messages/DETAILS.md` § Screenshots, plus the
headers of `apps/desktop/scripts/i18n-capture.ts` and `couple-screenshots.ts`): a capture-mode instruments
`t()`/`getMessage()`/`<Trans>` to record which keys each surface resolves, behind the build-time `__CMDR_I18N_CAPTURE__`
define so it's dead-code-eliminated from prod (verified prod no-op). A Playwright driver targets each window via the
`tauri-playwright` plugin's label-aware native screenshot and writes `screenshots/capture-report.json` (surface → keys).
The coupler (`couple-screenshots.ts`) reads that report and writes `@key.screenshot` line-surgically, plus a tracked
`screenshots/coverage-report.md` showing per-area what's coupled and which keys aren't.

**Native keys are exempt, and counted apart.** The harness drives a WEBVIEW, so it can never reach a string the OS
draws: the menu bar, the window title, the already-running alert. Those get their own `Native` column in the coverage
report rather than being filed under `Uncoupled`, so a permanent structural gap never reads as a surface the driver
forgot. ❌ Don't fake a screenshot for one; their `@key` descriptions carry the context instead, which is why they name
the menu, the verb-or-noun call, and the Finder counterpart.

**Leave the computer alone while a capture runs, say so before starting one, and make sure no other app is frontmost.**
A native screenshot returns the window's last COMPOSITED frame, and macOS stops compositing a window that isn't
frontmost, so clicking into another app mid-run makes the capture read a stale pre-paint frame and write a blank image.
An idle machine isn't enough: a browser left in front is the same condition, and the harness can't take the front back
from it. The app's title bar turns YELLOW and reads `SCREENSHOT` for exactly this reason: it's the at-a-glance signal
that a capture is in flight and the machine should be left to it.

Every shot is verified before the run may call itself green: the driver fronts the window, settles, waits for the whole
PNG to land, then decodes it and rejects a content-free image, retrying up to three times before failing the run with
the surface listed in `capture-failed.json`. It also refuses a frame a toast wandered into that the surface never staged
(a connected device announcing itself fires on its own clock, and lands translucent over an unrelated dialog). A
blank-shot failure points at the front position, not at a bug in the app or the harness: either the computer was in use,
or another app was simply sitting in front. Mechanism, guardrails, and the measured evidence for both:
`apps/desktop/src/lib/intl/messages/DETAILS.md` § Screenshots.

Framing follows what makes a translator's job easier, not one rule for everything. Most surfaces keep their whole
window, because the window IS the context; the registry-driven soft dialogs, toasts, and the per-tile indexing review
images are cropped to their own element, since the file panes behind them are the same in every one of those images. A
surface taller than its frame grows its WINDOW until the whole thing is in shot, and drops the UI zoom only when the
display itself runs out AND shrinking actually delivers the whole surface — translators judge text at its real size, so
a zoomed-out image earns its place only by being complete, and any surface captured that way is named in the coverage
report.

The surface set prunes itself the same way it grows. Every run reports the surfaces that resolved no key another
captured surface also has (`coverage-report.md` § Surfaces to review), so a set that only ever gained surfaces now has a
standing list of candidates to drop. It's a suggestion, not a verdict: a surface that adds no unique key can still be
the clearest picture of a key several surfaces share.

Most surfaces are hand-staged through the app's own triggers, which is the faithful way to photograph them. Soft dialogs
are the exception: they're mostly hard to evoke on purpose, so a final pass walks the DIALOG GALLERY's registry
(`i18n-capture-gallery.ts` driving `DIALOG_GALLERY_ENTRIES`) and opens each reviewable state over the main window. A new
soft dialog therefore gets a translator screenshot the day it gets a gallery row, with no harness change. That pass runs
LAST and photographs a state only when it resolves a key no earlier surface recorded, so a hand-staged capture of the
real path always beats a gallery preview of the same dialog, and the run doesn't write ~90 near-identical images.

**A surface that starts real work ends it, and says so when it can't.** Four surfaces need a live operation on screen
(the transfer-completion toast and the three queue shots), and an operation left behind holds its device lane, so the
next copy is admitted `queued` and never moves, and holds a queue row, so the queue window is never empty. One surface
walking away from a transfer parked on an unanswered clash failed all four, dozens of surfaces later, reading as four
unrelated timeouts with nothing pointing back at the cause. So every such surface cleans up through
`resetOperationState` (`i18n-capture-helpers.ts`), which cancels and then WAITS for the registry to empty, and reports a
drain that didn't happen rather than swallowing it. ❗ A clash can't be dismissed at all: `TransferProgressDialog`
withdraws its × and its Escape while one is up, because every exit from a clash decides something about the user's
files, so the only cleanups that work are answering it or cancelling the operation.

Two kinds of coupling raise coverage honestly:

- **Direct**: a key that rendered on a captured surface gets that surface's screenshot, a precise capture of its own UI.
- **Representative**: for a key still uncoupled after the direct pass that matches a curated prefix
  (`REPRESENTATIVE_SCREENSHOTS` in `couple-screenshots.ts`), the coupler writes a STAND-IN screenshot of the same
  panel/toast/dialog where the string appears, plus a `@key.screenshotNote` explaining the mapping (e.g. "this shows a
  different error, but your string is the title/explanation/suggestion in this same pane"). This sets translators up for
  success: it covers families with no captured surface of their own (the dynamic `errors.*` tail, AI/cloud states, SMB
  reconnect) AND shrinks the number of distinct images a translator loads. Direct always wins (a stand-in never
  overwrites a precise capture), and a representative only points at an image the run actually produced. The coverage
  report counts direct vs representative separately so a stand-in is never mistaken for a precise capture.

PNGs are gitignored and regenerable; what's TRACKED is `capture-report.json`, the coverage report, and the
`@key.screenshot` / `@key.screenshotNote` refs in the catalogs. A run that doesn't finish green rolls its rewrite of the
tracked files back (`createTrackedArtifactGuard` in `apps/desktop/scripts/capture-runtime.ts`): the report is written
DURING the run, because each mock pass loads it and merges its one surface back, so without the rollback a capture that
died halfway left the repo asserting couplings no complete run ever produced. Everything is written where the run's own
modules live, so a capture driven from a worktree writes into that worktree and never into the main clone. A warn-only
check (`message-screenshots-fresh`) flags when the couplings drift from the report, never a build failure, since
screenshots are an optional translator aid (description + key are enough to ship a locale). Coverage is partial until
the driver covers the full surface inventory.

Which families are still uncoupled, why each one resists capture, and what closing it would take:
`docs/specs/later/i18n-screenshot-gaps.md`. The live per-area numbers are always the generated
`apps/desktop/src/lib/intl/messages/screenshots/coverage-report.md`, never a hand-written figure.

## Raw families (`errors.*` and the native strings) are NOT ICU

⚠️ Translators and translator agents: two families invert the normal ICU rules, because neither reaches the ICU engine.
`errors.*` resolves raw through `getMessage()`, and the NATIVE families (`menu.*`, `licensing.windowTitle.*`,
`main.instanceLock.*`) are read by Rust's `menu_t`, which is a table lookup plus plain `.replace('{token}', value)`. So,
in any value from either family:

- **Use NORMAL apostrophes** (`doesn't`, not `doesn''t`): the opposite of every other catalog value, which doubles them.
  Enforced by `desktop-i18n-icu` across every catalog including `en`, so this one can't ship by accident.
- **`{token}` is a literal replacement target** (`{system_settings}`, `{path}`, `{reason}`, …): keep it verbatim, never
  add ICU formatting (`{x, plural, …}`, `{n, number}`), since none of it is parsed.
- **`<…>` is LITERAL text** (e.g. `<folder-path>`), not an inline component or tag.
- **`#`, backticks, `**` are markdown/literal\*\*, passed through untouched.

The canonical, fuller version of this note (and why the split is keyed on the prefix via `isRawKey()`) lives with the
code: `apps/desktop/src/lib/intl/messages/DETAILS.md` § `errors.*` are RAW. The locale checks honor the split (the ICU
check skips raw keys; the parity check compares their `{token}` set instead).

For the native families there's one more rule: a menu label's trailing `…` is the U+2026 character, never three periods,
and it means the dialog can change WHAT the command acts on (`Copy…` takes a destination) rather than merely that it
confirms (`Delete`). Keep it wherever English has it, and don't add one where English hasn't.

## Gotchas (hard-won)

- **The error pipeline bypasses ICU.** Listing/git/provider/write-error prose resolves via `getMessage()` (raw lookup),
  NOT `t()`: its `{system_settings}` `expandSystemStrings` tokens and `esc()` HTML entities collide with ICU's
  brace/apostrophe grammar. So error catalog values use NORMAL apostrophes and keep their composition/escaping logic in
  `$lib/error-messages/` (`compose.ts`). Don't route them through `format()`. The frozen golden fixture
  (`$lib/error-messages/__fixtures__/friendly_error_golden.json`) is the parity net: never regenerate it.
- **`<Trans>` tag names must differ from param names**: a tag named like a param silently overwrites the param value.
- **A literal `<` in a catalog value is parsed as a markup tag**, so ICU throws `UNCLOSED_TAG` at render. Escape it
  (`'<'`); this bit the `<dir>`/`<no perms>` size placeholders.
- **`keys.gen.ts` is generated** (`pnpm intl:keys`); never hand-edit. Dynamically-built keys (the error factories'
  ``getMessage(`errors.listing.${reason}.title`)``) read as "dead" to the static scanner; the error-level
  `desktop-message-keys-unused` check carries them via a closed dynamic-prefix allowlist so they don't fail the build.
  Both layers are documented in `messages/DETAILS.md` § Dead-key honesty + the orphan check.
- **Formatter parity**: en-US output is byte-identical to the pre-i18n code EXCEPT raw-byte triads (now comma-grouped,
  was a U+2009 thin space); human-friendly sizes use `useGrouping: false` to stay identical. Net `en-us-parity.test.ts`.
